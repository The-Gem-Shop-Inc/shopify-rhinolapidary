# Epic L discovery and context

**Epic:** L — Warranty, Service, Repairs, and Support
**Prepared:** 2026-11-05
**Disposition:** Planning only; ready for Product Owner review
**Implementation, Shopify mutation, app installation, email, publication, and production-data authority:** Not granted

## Executive finding

Rhino has a strong repository foundation for Epic L but almost no approved support-domain data. Existing contracts can identify Products, Variants, approved compatibility, machine-family relationships, and five classes of support Files. Existing customer paths provide a neutral Contact form and a Manuals index. Those foundations must be extended, not replaced.

The release-safe state is intentionally sparse:

- warranty policy, role, class, and Product mapping approvals are all zero;
- the indexed resource corpus contains 110 candidates, including 74 Shopify File identities, but zero canonical resources and zero publication approvals;
- the machine-page warranty and resource renderers are fixture-only and cannot render on a real storefront host;
- the native contact form is unstructured and has no machine, serial, request category, proof-of-purchase, upload, consent, routing, deduplication, or service-status contract;
- support hours, response commitments, repair eligibility, pricing, shipment responsibility, retention, discontinued-product support, service-center eligibility, and recall ownership are not approved;
- current Shopify Forms, Flow, Inbox, customer-account, and app-embed state has not been freshly audited for Epic L.

Epic L should begin with repository-only authority, policy, privacy, and current-state work. It should not begin by publishing the historical warranty PDF, enabling a form, or creating a custom support application.

## Reusable data and implementation architecture

| Relationship | Existing authority | Epic L conclusion |
|---|---|---|
| Machine model → Product | `data/epic-e-product-identity.json`, current Product GIDs/handles | Reuse exact Product identity. Do not create a second machine registry. |
| Product → Variant | Native Shopify Product/Variant identity and current catalog audits | Reuse native references; intake may capture an optional Variant only when relevant. |
| Product → class | `PRODUCT:rhino.product_class` (`CD-MF-001`) | Reuse for routing and eligibility; never infer from title/tag/type. |
| Product → machine family | `PRODUCT:rhino.machine_family` and `METAOBJECT:machine_family` | Definition exists, but membership/instances are absent. Family navigation must remain conditional. |
| Part → compatible machine | `PRODUCT:rhino.compatible_machines` (`CD-MF-034`) and Epic G/F consumers | Reuse exact Product references. Epic L owns support presentation, not fit approval. |
| Product → manual/diagram/instruction/video/support File | `CD-MF-041` through `CD-MF-045` | Reuse definitions and E resource lifecycle. `support_files` is Admin-only and must not become a customer download. |
| Warranty policy/version/class/mapping | Epic E Batch 3C repository architecture | Zero approvals. Decide policy/roles/mappings first; create no warranty metafield/metaobject until justified. |
| Serial number → owned machine | None | Treat as private support/registration data. Do not attach arbitrary serials to public Product metafields. Define format, validation, ownership, and access first. |
| Purchase evidence | Native Order identity when available; otherwise none | Prefer authenticated/order-linked evidence where possible. Uploaded documents require an explicit private storage/retention model. |
| Troubleshooting symptom/maintenance procedure | None approved | Choose Pages/blogs/metaobjects only after content lifecycle, reuse, revision, and search needs are known. Do not overload File lists with workflow state. |
| Request category/status | None | Shopify Forms/Flow may handle intake/routing; a durable service-status model requires additional architecture and may belong to an app/CRM. |

The approved custom-data architecture favors native Shopify fields, typed references, and additive contracts. A new “support platform” metaobject should not be created merely to mirror Pages, Files, Products, or form submissions.

## Operational decisions the business must supply

No source currently authorizes the following facts:

- current warranty issuer, administrator, covered Products/classes, duration, trigger, exclusions, remedies, registration effect, proof-of-purchase requirements, transferability, geography, and policy effective/version dates;
- manufacturer versus seller responsibility for each relevant machine/product class;
- service eligibility, diagnosis boundaries, repair authorization, estimates, labor/parts pricing, customer approval, declined-repair handling, turnaround communication, and record ownership;
- safe packaging, inbound/outbound freight, insurance, loss/damage responsibility, carrier claim responsibility, and repair-shipment instructions;
- staffed channels, hours, holidays, response targets, emergency/safety escalation, and language/geographic coverage;
- serial-number formats and whether legacy equipment can be verified;
- supported/discontinued/unknown status and the promise, if any, made for each status;
- dealer/service-center qualification, geographic scope, current status verification, and directory owner;
- recall/safety-notice authority, legal review, affected-unit matching, publication/removal, direct notification, and audit retention;
- request-data retention, staff access, deletion, export, incident recovery, and whether uploaded documents are necessary.

These are human acceptance gates. A validator can detect a missing approval, stale policy version, or unmapped Product; it cannot manufacture the approval.

## Native Shopify feasibility

Current official Shopify documentation supports a native-first investigation:

- Shopify Forms supports inline/support forms, custom fields, a single upload up to 20 MB, notifications, customer/customer-metafield storage, and Flow integration. It does not support multi-step forms or conditional logic. Submission data creates or matches a customer profile, which is material to consent, deduplication, access, and deletion decisions. See [Forms settings](https://help.shopify.com/en/manual/promoting-marketing/create-marketing/forms-app/settings/all-forms), [create forms](https://help.shopify.com/en/manual/promoting-marketing/create-marketing/forms-app/create), and [manage submissions](https://help.shopify.com/en/manual/promoting-marketing/create-marketing/forms-app/manage).
- Shopify Flow is available as a free app on Basic, Grow, Advanced, and Plus, but the Send HTTP Request action is limited to Grow, Advanced, and Plus. Flow is plausible for tags, internal notification, and bounded routing after a current plan/configuration audit. See [Shopify Flow](https://help.shopify.com/en/manual/shopify-flow).
- Shopify Inbox can configure staffed availability, automatic first replies, and instant answers. It is not a service-record system, and current Rhino enablement/configuration is unverified. See [Inbox availability](https://help.shopify.com/en/manual/inbox/chat-settings-and-appearance/availability-and-first-reply) and [Inbox settings](https://help.shopify.com/en/manual/inbox/chat-settings-and-appearance).
- New customer accounts support app UI extensions and full-page/account-order pages. Legacy accounts do not support customer-account UI extensions. A saved-machine or service-record dashboard therefore depends on Epic O, the actual account mode, a data backend, and app approval. See [building customer-account apps](https://shopify.dev/docs/apps/build/customer-accounts) and [full-page extensions](https://shopify.dev/docs/apps/build/customer-accounts/full-page-extensions).
- Shopify Messaging supports post-purchase email automations, but audience/consent, transactional versus marketing purpose, machine identity, and content approval must be resolved before activation. See [marketing automations](https://help.shopify.com/en/manual/promoting-marketing/create-marketing/shopify-messaging/marketing-automations/create).

The native capability evidence establishes feasibility, not permission to install, configure, activate, or send.

## Technical, privacy, and recovery requirements

Epic L intake and service records must:

- collect the minimum necessary data and explain why serial numbers, photos, or proof of purchase are requested;
- separate public Product/resource data from private customer, order, serial, and service records;
- allow only authorized staff access and record the system of record;
- define retention/deletion/export for submissions and files, including customer privacy requests;
- constrain file type/size, scan or safely handle untrusted uploads, and never publish uploaded evidence;
- use stable request identifiers, safe retry, duplicate detection, and an explicit uncertain-submission state;
- retain entered values and provide accessible error recovery without exposing customer data in URLs, logs, screenshots, analytics, or theme settings;
- fail closed when machine identity, warranty authority, or resource approval is unknown;
- version manuals, policies, articles, and notices with effective/current/superseded states;
- document notification failure, queue/routing failure, staff escalation, outage fallback, and operational reconciliation;
- meet the existing form-state, app-dependency, privacy-review, accessibility, responsive, and performance policies.

## Validation opportunities

Extend existing infrastructure rather than introducing competing systems:

- Epic E registry and definition validators for resource/warranty mappings;
- Epic F support-resource fixtures for real-host safe suppression and approved-resource rendering;
- Epic G exact compatibility validators for parts lookup;
- C/D navigation/footer/homepage route validators for new support destinations;
- brand-claims validation for unapproved warranty, response-time, repair, availability, and safety claims;
- deterministic form fixtures for required/optional fields, long/malformed values, spam controls, duplicate/retry/uncertain states, upload rejection, routing failure, and privacy minimization;
- Playwright accessibility, keyboard, 200% zoom, 320/360/390 mobile, tablet, desktop, slow/failure, and authenticated/anonymous scenarios;
- broken-link/File-reference/revision/language/duplicate/orphan detection;
- release readback that distinguishes repository, Shopify Admin, content, operations, app, email, and production evidence.

## Recommended initial scope

Start with Batch L1 (`L-PBI-001` through `L-PBI-005`) as repository-only work:

1. bind current sources and drift rules;
2. prepare warranty and service decision packets without approving their answers;
3. approve privacy/data-minimization rules;
4. perform a separately authorized read-only Admin capability audit;
5. record owners and current-state evidence.

L1 can proceed without publishing a warranty duration, making a repair promise, installing an app, creating a form, or modifying Shopify. L2–L4 should not start implementation until the applicable L1 human gates are satisfied.

## Machine-readable planning assessment

`docs/project/epic-l-proposed-backlog.json` is the smallest useful machine-readable planning layer: it records all 28 identifiers, statuses, priorities, efforts, evidence states, owners, dependencies, six batch memberships, the safe initial batch, and explicit false authorization flags. `scripts/validate-epic-l-planning.js` checks sequential/unique IDs, allowed values, dependency and batch integrity, every required detailed tracker field/subsection, decision/findings/transition evidence tokens, all ten handoff sections, complete handoff inventory, and the planning-only boundary.

Do not introduce a second evidence schema or standalone dependency-graph file yet. Existing Epic E/F/G/K registries already govern sources, resources, compatibility, decisions, and receipts; the proposed backlog already supplies the planning graph. Add a domain evidence schema only within an approved L-PBI-001/L-PBI-006 extension when the approved support facts require fields the current contracts cannot represent.
