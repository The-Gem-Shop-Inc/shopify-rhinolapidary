## F/G relationship interface

`schemas/epic-f-context-delivery.schema.json` defines a packet for one exact machine GID with at most 32 supplied edges and 12 operational records. `reverseProjection` accepts this bounded input, exact page configuration and the F4 projection; `projectContextDelivery` computes F4 facts through the existing consumer before applying page precedence. There is no browser fetch, catalog-wide reverse query or discovery UI. Output is validated against `epic-f-context-delivery-projection.schema.json`; a non-fixture output cannot contain cards, delivery facts or a policy link in this batch.

Every card retains the original dependent Product GID, target machine GID, edge identity, source and approval identifiers, audience, lifecycle, effective/expiry times, activation and Product/Variant/configuration scope. Approved compatibility additionally requires the existing consumer to verify the dependent Product's exact `compatible_machines` migration row and its positive machine reference. Contextual accessory/consumable relations remain separately labeled; neither supplies compatibility. There is currently no approved live contextual value adapter, so a real reverse module stays absent.

The consumer's compatibility subject check now follows E's approved dependent classes (replacement part, consumable, accessory), instead of requiring a machine to own the dependent field. Other domains keep their machine subject checks. Every original approval, type/value, reconciliation, currentness, audience and activation condition is retained. Fixtures use the existing WeakMap approval simulation and cannot survive serialization or changing `fixtureOnly` to false.

Original SawMaster edges EDGE-001, EDGE-002, EDGE-005 and EDGE-006 remain blocked and unapproved. Tests inspect their real negative states. Positive fixtures use synthetic review sources and unrelated synthetic relationships to the BeadMaster fixture route; none asserts the disputed SawMaster fit.

Product scope is explicit. Dependent Variant scope requires an exact registered Variant/parent pair and displays an associated Variant label without selecting that Variant or adding query parameters. Configuration scope requires the exact page configuration and preserves its label; an unexpressible/mismatched scope disappears. No universal compatibility is inferred from narrower fit.

Targets require exact governed identity and class, exact handle binding, active/published customer visibility, fresh observation and current lifecycle. Missing, deleted, unpublished, stale, wrong-class or audience-denied targets are diagnosed and suppressed. No successor matching occurs. Duplicate edge IDs or duplicate dependent targets suppress all ambiguous candidates deterministically.
