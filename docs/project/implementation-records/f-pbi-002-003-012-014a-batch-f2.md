## Implementation and decisions

One shared `templates/product.machine.json` reuses Trade `main-product`, `product-info`, native title, price, Variant picker, quantity, buy buttons, pickup and Product-form JavaScript. It has exactly six blocks in that order, ending in neutral Contact. Price supplies native Sold out status; buy buttons supply exact selected-Variant availability. The inventory prose block is not included. No machine family templates, specification data, optional module placeholders, navigation anchors, gallery activation or sticky purchase controller were added. [ADR-0001](../../architecture/adr-0001-product-template-architecture.md) now accepts this decision.

F1 already collapses suppressed media into Trade's no-media layout. The additional machine-scoped Rhino styles ensure long titles, prices, pill labels and buttons wrap. Native purchase code, default `product.json`, Contact page template and Contact form are pinned by normalized source hashes; negative tests prove edits fail the regression contract. The default non-machine render still exposes its existing description and native purchase controls without machine Contact styling.

The F1 consumer validator's original prohibition on a machine template was a batch sequencing assertion. It now requires the real machine template to use F1-contained `main-product` and the fixture to expect `product.machine`. All fact, generation/provenance and containment assertions remain. The general Product template validator now requires the machine template and its complete native purchase block set.

## Native purchase evidence

Deterministic fixtures cover tracked available, tracked unavailable with positive stock, zero-stock DENY, untracked available, missing/invalid Variant, native minimum-quantity sold-out, draft and unpublished routing. Product-level availability/price deliberately disagree with selected-Variant state in negative fixtures. Native disabled/Sold out/Unavailable labels remain authoritative.

The browser loads real repository Liquid/snippets, native `global.js`, `product-info.js`, `product-form.js`, pickup scripts and CSS. Variant events receive intercepted section HTML rendered from the same section. Tests prove available → Sold out → Unavailable → available transitions, ID synchronization in both native forms, quantity buttons, exact selected Variant submitted once, valid quantity and native error/alert recovery for an invalid quantity.

Trade uses `novalidate`; invalid quantity is tested through the existing server-error response path, not a new Rhino validation policy. No-JavaScript evidence covers existing POST action, selected ID, quantity association, button and Contact link. This does not claim enhanced no-JavaScript Variant selection. All requests are intercepted on `machine.local`; external hosts are aborted. No actual storefront cart request occurs.

Draft/unpublished 404 fixtures model the Shopify routing boundary before Product rendering. They are not a new Liquid publication gate and do not prove current live publication state. Fixture commerce data and the synthetic second Variant are test-only, not approved customer facts.

## Contact/context boundary

The visible label is localized `Contact`; destination is exactly `/pages/contact`. Existing Contact page/form sources are unchanged. The link works without context, scripts or query consumption. A local route fixture verifies link activation; actual Shopify rendering remains deferred.

`scripts/lib/epic-f-contact-context.js` is a dormant, strict object validator, with no storefront imports, URL builder, submitted fields or persistence. The only accepted keys are exact governed machine `productGid`, optional matching known `variantGid`, and exact relative `productRoute` from Epic E identity. These values authorize no facts, compatibility, price, availability or publication state. Source registers provide routing identity only; their other pending approvals remain unchanged.

Unknown keys, non-string values, unknown IDs, mismatched pairs, arbitrary/external/protocol-relative URLs, encoded paths, query/fragment/redirect parameters, free-text/customer fields and injection payloads are rejected. Accepted GID/route alphabets contain no HTML metacharacters; the validator returns a frozen data object, never HTML. Any future output sink must still use its own HTML/URL escaping. There is no assumption that Shopify Contact consumes query parameters. Activation requires Epic P routing, privacy, retention and submitted-data ownership and a fresh governed identity review.

## F-PBI-014A harness and limits

The dedicated local Playwright configuration does not load preview credentials or the live preview configuration. At 320, 360, 390, 768, 1024, 1440 and 1920 px, six shell states each assert one semantic H1/main, source order, keyboard hierarchy, visible focus, accessible control names, labels/disabled semantics, keyboard Contact, absent media/empty groups/focus targets, no page overflow and no browser errors. Axe serious/critical findings must be zero for every tested shell.

Long unbroken titles/options, long prices and purchase labels are tested at every width, including 200% root-font text enlargement. That simulation is explicitly not browser zoom. A separate extension-assisted Chromium test uses actual `chrome.tabs.setZoom(2)` and verifies halved layout viewport and doubled device pixel ratio plus reflow. No CDP pinch-zoom substitution is used.

The local renderer adapts Shopify form tags, translation/money/color/font drops and platform filters; native `payment_terms` provider output is empty in fixtures and is not fabricated. Local font drops use Arial fallback. This is executable shell regression evidence, not full Shopify-renderer, provider or production-font parity.

Global header/footer are outside this isolated shell harness. Existing text-enlargement/global-chrome findings remain under Epic C and are not marked resolved. Preview snapshots, current live publication routing and renderer parity remain separately authorized future checks.
